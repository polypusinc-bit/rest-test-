HOW TO USE
1. In 3D choose Edit ingredients. In WebXR, first place the dish; editing then
   becomes active. Reposition dish switches back to the viewer's placement mode.
2. Spread ingredients to reach hidden layers. Tap a visible ingredient to select.
3. Drag it into the bin and release, or tap the bin after selecting it.
   A labeled ghost follows your finger. The actual ingredient mesh does not move
   with the finger; the rest of the dish remains anchored.
4. Release outside to cancel. A valid removal stacks the dish using its existing
   recipe poses, updates the controls/price, and prepares the iPhone recipe file.
5. Undo restores the complete previous recipe AND layout. Add items back using
   the ingredient tray/buttons. Reset restores configured defaults.
6. Pepperoni slices are a single configured group; Extra pepperoni is separate.
   Fixed chicken, sandwich buns, and pizza crust/sauce cannot be selected.
   Burger's existing bun controls remain editable to preserve its configuration.

ENGINEERING / PRESERVATION
Active: menu.html/index.html/dish.html -> app.js/app.css -> ar-viewer.js.
New: ingredient-interaction.js (gesture state), ingredient-editor.js (UI),
picking-adapter.js (only compatibility bridge to pinned model-viewer 4.1.0).
Recipe state, prices, persistence and native packaging use the same commit path
as conventional ingredient controls. Transitive dependencies now normalize to
completion regardless of option order. Undo is one step and includes dependents.

materialFromPoint is the public picking API. Version 4.1.0's internal scene
getHit ignores opacity, so the adapter temporarily marks wholly invisible
meshes noHit, restoring every flag in finally. It never changes model geometry.
Opaque fixed geometry blocks picking underneath. Current material IDs map to
logical options, including repeated pieces and multiple materials. Ambiguous
mappings are rejected. Object IDs are supported by the shared resolver; current
models use material picking. New assets with shared materials need preparation.

The same isolated adapter corrects XR screen coordinates against the overlay
bounds because 4.1.0 normalizes against window.screen dimensions. Its active
XR camera and current animated meshes perform picking. This source inspection
and mocked coordinate tests do NOT verify real-device accuracy.

Only the local edit surface and controls prevent beforexrselect. Move mode
passes placement gestures through. The documented exit-webxr-ar-button slot
connects the Back button to the viewer's real session exit. No fake exit method.
Pointer cancellation, tracking loss, blur, resize, page hide, mode change, tray
opening and AR exit clear gesture visuals. Highlighting temporarily changes
emission only, restoring the prior values. Base color, textures and opacity
are preserved. If picking compatibility fails, conventional controls remain.

All GLB/USDZ assets, recipe-package.js, animation order, model-viewer dependency,
scale, placement, and Quick Look files are byte-identical to the v5 baseline.
No new dependencies, services, accounts, dashboards or checkout were added.
Versioned entry points and imports use v=6; unchanged package writer stays at
its existing version. Existing restaurant/dish links and state keys remain.

SMALLEST REALISTIC PATH TO EQUIVALENT IPHONE CAMERA GESTURES (PROPOSAL ONLY)
Build a small native iOS companion using ARKit world tracking and RealityKit
ARView, while retaining this website and Android path. Use per-ingredient
entities/collision shapes and screen-space native UI. Existing source models
can be reused, but entity/collision preparation and import validation are
required; the current merged skeletal USDZ is not automatically an editable
entity hierarchy. Use the same menu IDs/pricing rules and a deliberate bridge
for returning a complete recipe to the website.

Hosting: existing public menu/config/assets can stay on HTTPS GitHub Pages.
No tracking server is required. App distribution and any universal-link domain
association are separate setup; a suitable domain may be needed for that route.
Tracking: real six-degree-of-freedom ARKit plane/world tracking, not a model
pasted over a camera video. Dependencies: Apple's SDKs, Xcode and native Swift
code; no commercial web-AR service is introduced. Licensing: Apple SDK and
Developer Program terms apply; public/beta distribution needs the appropriate
membership, while personal-device Xcode testing has provisioning limitations.
Maintenance: an additional iOS app, native gestures, collision assets, recipe
synchronization and OS/device QA. It adds install/distribution friction.
This is an engineering recommendation, not an implemented feature or estimate.
Approval is needed before starting that framework/app change or paid enrollment.
